Crest

|View as Markdown

Overview

Crest is a command line application for Phalcon. It generates code, shows information about a project, and creates and runs projects.

Crest works with two flavors of project, mvc and adr:

  • MVC (Model-View-Controller): models, views and controllers, in the layout of vokuro and invo, the Phalcon sample applications.
  • ADR (Action-Domain-Responder): an action for each route, and a responder that the action calls. A route is an HTTP method and a path that the application answers, for example GET /. The action answers the route, and the responder makes the response. An ADR project can also have middleware: classes that a request goes through before it gets to the action.

Requirements

  • PHP ^8.1, with the tokenizer extension (ext-tokenizer; PHP turns it on by default)
  • Phalcon v5, the ext-phalcon C extension (^5.18), or Phalcon v6, the phalcon/phalcon PHP implementation (^6). Crest itself needs neither of them to run

How Crest Works

This section explains the parts of Crest that the rest of this page uses: The Project File, The Global Crest and the Project Crest, The Runtime, The Launcher and Stubs.

The Project File

Each project has a crest.php at its root. This is the project file. crest new writes it. For an existing project, crest init writes it (see Adding Crest to an Existing Project). The file holds the settings of the project, for example:

  • the flavor
  • the root namespace
  • the front controller (the class that starts the application)
  • the folders that Crest writes into
  • the runtime (see The Runtime)

The bootstrap key names the front controller (see Commands That Boot the Project). Configuration shows each key.

Crest finds the project by its crest.php: the file that --config names, or the nearest crest.php in or above the working directory or --directory (see Global Options). Without crest.php, Crest stops. This error is the same in both flavors:

The Global Crest and the Project Crest

The commands that work on the project, for example make:controller, make:action and route:list, need the autoloader and the Phalcon of the project. The Runtime

The runtime key of crest.php says where the project commands run:

  • With ['type' => 'host'], a global Crest runs the project’s vendor/bin/crest with the PHP of the host.
  • With ['type' => 'docker', 'service' => 'app'] (what crest new writes), a global Crest runs docker compose exec app vendor/bin/crest ... in the project root. app is the service: a container that the compose file of the project names.

Use docker when Phalcon is only in the container. For example, a v5 project then works on a host without ext-phalcon. The containers must be up (crest up).

The docker runtime has two conditions. The compose file that crest new writes, docker-compose.yml, meets both:

  • The service must mount the project folder (share it with the container), with vendor/ in it: Crest looks for vendor/bin/crest on the host first.
  • The working_dir of the service, the folder where its commands start, must be the project root: vendor/bin/crest runs there.

crest install runs composer in a docker compose service, with each runtime. With the docker runtime, composer runs in the service of the runtime. With the host runtime, composer runs in the service of the runtime key, else in app.

crest serve is the exception: it always runs on the host, because PHP’s built-in server must listen there. With docker, crest up serves the project.

The Launcher

./crest is a launcher script that crest new writes into the project. It needs docker only: PHP on the host is not necessary.

./crest up, ./crest down and ./crest install run docker compose on the host: they start the containers, stop them, and install the dependencies. With a global Crest, crest up and crest install do the same. Crest runs up, down and install with docker compose in the folder of the crest.php that it finds (see The Project File).

All other commands of ./crest run vendor/bin/crest in the service of the project (app, or the --service of new; see Creating a Project):

Before ./crest install, they stop with crest: run './crest install' first. Without a terminal (CI, a pipe), the launcher adds -T, which tells docker compose exec not to ask for a terminal. On Windows, run ./crest in WSL2.

The .env file of the project holds settings that docker compose reads, for example APP_PORT and the user and group IDs (UID and GID). The files that the container writes belong to the user of these IDs. With rootless docker (docker that runs without root), set UID=0 and GID=0 in .env: rootless docker maps root in the container to your user.

The Crest commands of the launcher get CREST_HOST_ROOT, the host folder of the project. Thus Crest shows host paths, not the paths in the container. The hand-off of a global Crest does the same.

The launcher runs vendor/bin/crest. If you change vendor-dir or bin-dir in composer.json (see Configuration), change the crest= line at the top of ./crest.

Stubs

Crest generates files from stubs. A stub is a template in the Crest package, with placeholders such as {{ flavor }}: Crest fills in each placeholder with a value of the project. To change a stub, publish a copy with crest stub:publish, and edit the copy. Crest then uses your copy. crest new writes a project from the project-* stubs, for example the project-config stub for crest.php. Custom Stubs and Project Stubs tell where each copy goes. For the project-config stub, see also Commands after new.

Some generators also write a base: a class that Crest owns and writes again, for example CrestControllerBase, which your controllers extend. Generated Bases tells when Crest writes a base again.

Creating a Project

crest new creates a project. It writes an MVC or an ADR project that runs:

An MVC project has public/index.php (the web entry point) and the front controller src/AppFront.php. It also has crest.php, composer.json, the docker files, and src/Controllers/IndexController.php, which answers GET /. For more, see The MVC Project. An ADR project has the same entry point, front controller and files, and src/Action/Get.php, which answers GET /.

new takes the options in the table below. The view engine (the --template-engine row) renders the views of an MVC project: with phtml, the views are PHP templates in .phtml files, and with volt, they are Volt templates in .volt files (see Volt). --camel-case and --get-set change the models that make:model writes from the database tables (see Generating Models). They set the models key of crest.php (see Configuration).

Option Purpose
--flavor=mvc|adr the flavor of the project; defaults to mvc
--template-engine=phtml|volt|none the view engine of an MVC project: phtml, the default, volt (see Volt), or none for a project with no views (see The MVC Project). An ADR project has no views, so new stops when you give it
--namespace=<name> root namespace for the generated code; defaults to App
--php=<major.minor> PHP version for composer.json and the Dockerfile; defaults to 8.4, and must be 8.1 or later
--phalcon=v5|v6 v5 requires the C extension, 5.18 or later; v6 the phalcon/phalcon package; defaults to v5
--runtime=host|docker where the project commands run (the runtime key of crest.php); defaults to docker
--service=<name> the docker compose service, for docker; defaults to app
--database=none|mariadb|mysql|pgsql|sqlite the database of the project; defaults to none. See The Database
--camel-case for MVC: property names in camelCase (models.camelCase of crest.php). See Names
--get-set for MVC: protected properties with a getter and a setter (models.getSet of crest.php). See Getters and Setters
--force write into a directory that is not empty, and overwrite files with the same names

In a terminal, new asks for each value that no option gives:

  • the flavor
  • the view engine, for MVC
  • the namespace
  • the PHP version
  • the Phalcon version
  • the runtime (host or docker)
  • the service, for docker
  • the database

For an MVC project with a database, new asks two more questions. First, it asks if the property names of the models are in camelCase. Then it asks if the properties are protected, with a getter and a setter.

An empty answer takes the default. --no-interaction (see Global Options), or a run without a terminal (CI, a pipe), asks nothing and takes the defaults. The options still give their values, for example in CI.

The project goes into the folder <name> in the working directory, or in --directory if you give one (see Global Options). By default, new runs nothing: no composer, no docker, no network. It writes the files and prints the next steps. For an MVC project with no database, Quick Start shows the output.

To make new run commands, see Commands after new. To change the files that new writes, see Project Stubs.

The MVC Project

crest new my-app --flavor=mvc writes the layout of the Phalcon sample applications (vokuro, invo). The table below uses these Phalcon terms:

  • The DI (dependency injection) container of the application holds its services: the objects that the application uses. These are not the docker container and the docker compose service of The Runtime.
  • FactoryDefault is the Phalcon DI container with the default services.
  • A provider is a class that registers services in the DI container.
  • Phalcon\Mvc\Application handles each request.
  • The dispatcher loads the controller of a URL and calls it.
Path Contents
public/index.php the web entry point, as in an ADR project
src/AppFront.php the front controller: FactoryDefault, the providers and Phalcon\Mvc\Application
src/Providers/ DispatcherProvider (the default namespace of the controllers), UrlProvider (the base URI of the links and the redirects) and ViewProvider (the views folder and the phtml engine, or Volt: see Volt)
src/Controllers/ IndexController, which answers GET /
src/Controllers/Base/ CrestControllerBase, the base that Crest owns (see Generated Bases)
themes/default/ the layout index.phtml and the view index/index.phtml

crest.php has 'flavor' => 'mvc' and the paths (the folders that Crest writes into) command, controller, form, model, module, provider and views (see Configuration). To add a service, run crest make:provider Mailer. It writes src/Providers/MailerProvider.php, a provider that implements Phalcon\Di\ServiceProviderInterface. It also prints the line to add to AppFront::providers(), the list of the providers of the front controller.

With --template-engine=none, the project has no views, for example an application that only returns JSON. new writes no ViewProvider, no layout and no view, and crest.php has 'views' => false. The front controller calls useImplicitView(false): without it, Phalcon\Mvc\Application needs a view service for each request. IndexController returns its response, {"status":"ok"}. In this project, make:scaffold stops, because it writes views. make:module writes no views folder, and make:controller names no view.

A URL with no controller stops in the dispatcher (“handler class cannot be loaded”). With display_errors off, PHP answers 500. With display_errors on, PHP shows the error in the page, with status 200. Add a not-found page if your project needs one. For example, use a dispatcher listener (a class that gets the events of the dispatcher), such as the NotFoundPlugin of invo.

The Database

--database gives the project a database, in each flavor:

Choice The service in docker-compose.yml The PHP extension
none none; the default none
mariadb database, with the image mariadb:11.4 pdo_mysql
mysql database, with the image mysql:8.4 pdo_mysql
pgsql database, with the image postgres:18 pdo_pgsql
sqlite none: the database is the file storage/database.sqlite pdo_sqlite, which the php image has

With a database, new also writes:

  • DbProvider.php in the provider folder (src/Providers for MVC, src/Provider for ADR). DbProvider registers the db service: the connection to the database (see The MVC Project for services). In an MVC project, db is a Phalcon\Db adapter, which the models use. In an ADR project, db is a Phalcon\DataMapper\Pdo\Connection, which the repositories use (see Generating Repositories). The MVC front controller adds DbProvider in providers(). The ADR front controller gets an override of registerProviders(), the method that registers the services. The override calls DbProvider.

  • The connection values at the end of .env:

    DB_NAME is the project name, with _ in place of -, cut to 64 characters. DB_USERNAME is the same name, cut to 32 characters. For sqlite, .env has only DB_NAME=storage/database.sqlite, relative to the project root.

  • For mariadb, mysql and pgsql: the service database in docker-compose.yml, with a named volume for its data and a health check. The app service starts when the database accepts connections. Thus crest make:model works right after crest up and crest install. The database listens on the host only at 127.0.0.1, on the port DB_PUBLISHED_PORT: other computers cannot connect to it.

  • For mariadb, mysql and pgsql: the PDO extension in resources/docker/Dockerfile.

  • phalcon/phql in composer.json, for an MVC project with Phalcon v6. PHQL is the query language that a model uses to find rows (see Generating Models).

  • For sqlite: the empty file storage/database.sqlite (an empty file is a valid SQLite database), storage/.gitkeep, and /storage/database.sqlite in .gitignore. --force does not replace a database file that exists: git ignores the file, so nothing can restore its data.

docker compose gives the values of .env to the app container. PHP on the host does not read .env. There, DbProvider uses its defaults: 127.0.0.1 and the published port. DbProvider reads each value from getenv(), then from $_ENV, then takes the default.

A loader such as phpdotenv (a PHP library that loads .env) also reads .env on the host. There, DB_HOST=database is not a known host. Then give PHP on the host DB_HOST=127.0.0.1 and DB_PORT (the published port) in its environment: getenv() wins over $_ENV.

To run the project with PHP on the host, start only the database, and install the PDO extension on the host:

If the port is in use on the host, change DB_PUBLISHED_PORT in .env. Then PHP on the host needs DB_PORT with the same value in its environment. The MySQL and MariaDB images do not accept the user root. Thus a project with the name root needs another DB_USERNAME.

The db service is shared. It connects when the project uses it for the first time, for example at the first query of a model. Thus the project answers GET / when the database does not run. A wrong value gives the connection error at the first use of db.

With mysql, mariadb or pgsql, the app service cannot have the name database:

In an ADR project with a database, the front controller already has registerProviders(). For a new provider, crest make:provider prints only the provide() line to add to it. provide() is the method of a provider that registers its services. Crest reads the front controller from the bootstrap key of crest.php. When it cannot load that class, it prints the whole override.

To change the service or the .env lines of the database, for example the image, see Project Stubs.

To add a database to a project that exists, see Adding a Database.

Adding Crest to an Existing Project

For an existing project, crest init writes crest.php (see The Project File). If the project does not require Crest yet, add it as a dev dependency first. The composer require command needs the version dev-master (see Installation). The commands are the same in both flavors:

init writes crest.php in the nearest folder with a composer.json. The psr-4 map is the autoload.psr-4 part of composer.json: it gives a folder to each namespace prefix, for example "App\\": "src/". The generators (the make:* commands) get their namespaces from this map. Thus init needs a psr-4 entry in composer.json. Without one, init stops and tells you to add one, for example "App\\": "app/", and to run composer dump-autoload.

init asks these questions, in this order. For each question, it proposes a value that it finds in the project:

  1. The namespace. The proposal is the namespace of the first psr-4 entry whose folder exists. The answer must be in the psr-4 map (App\Api under "App\\": "src/" is). The other proposals follow the answer: its folder is the psr-4 folder of the longest prefix, for example src/Api.

  2. The flavor: mvc or adr. For each flavor, init counts the default folders of that flavor (item 4) that the project has. It proposes the flavor with the most. A tie gives mvc. A project with src/Controllers, src/Providers and themes/vokuro gets mvc. --flavor answers the question.

  3. The front controller: <namespace>\AppFront when AppFront.php is in the folder of the namespace. Answer none for no front controller.

  4. A folder for each path of the flavor (the paths key of crest.php; see Configuration). The MVC paths are command, controller, form, model, module, provider and views. The ADR paths are action, command, middleware, provider, repository and responder. The question says if the folder exists. A class folder is in the folder of the namespace. An answer must be a relative folder in a psr-4 folder. Its folder names must give a usable namespace: src/my-actions gives App\my-actions, which PHP cannot use. init removes a leading ./.

    views holds no classes. It is a relative folder in the project, with no psr-4 check. Each part of the answer must be a folder name. Thus init refuses an absolute folder, an empty part (//), . and ... The proposal is themes/default. When that folder does not exist and themes/ has one folder only, init proposes that folder (themes/vokuro in vokuro). The answer none is a project with no views: init writes 'views' => false (see The MVC Project).

Running a Project

A project runs with docker, or with PHP on the host (see Quick Start). For the Crest that runs up, down and install, see The Global Crest and the Project Crest.

With docker, use crest up, crest install and crest down (see The Launcher). crest down stops and removes the containers. up --build rebuilds the image first, and down --volumes also removes the named volumes.

Without docker, crest serve starts PHP’s built-in web server for the project (see With PHP on the Host). .htrouter.php is the router script of PHP’s built-in server. serve runs php -S 127.0.0.1:8080 -t public .htrouter.php in the project root. The router and the document root (public) are the same as in the container.

The port is --port, else APP_PORT from the environment, else APP_PORT in the project .env, else 8080. docker compose reads APP_PORT in the same order.

serve reads .env as docker compose does: the last APP_PORT line wins, and export, APP_PORT: <port>, quotes and # comments are allowed. serve does not expand ${...}: a value with ${...} stops serve with an error.

serve finds the project root from a subfolder. A global Crest passes serve to the Crest in vendor/, as it does the other project commands (see The Global Crest and the Project Crest). serve stops before PHP starts if .htrouter.php or <vendor-dir>/autoload.php is missing. vendor-dir is a setting of composer (see Configuration).

The server uses the PHP that runs Crest. PHP options on the command line, for example -d extension=phalcon.so, do not reach the server. Put such settings in php.ini.

Press Ctrl+C to stop the server. If the server continues to run, for example after Crest stopped in a different way, stop its PHP process. The command is the same in both flavors:

When make:model Stops

Crest stops, and writes no file, when:

  • the table name gives no class name (user-profiles), or a name that PHP reserves (list), and models.classes gives it no class (see Names);
  • the project has no db service, the service is not a Phalcon database adapter, or it cannot connect;
  • the table does not exist (in the schema of models.schema, when you set it);
  • models.schema has a value, and the db service is SQLite (see The Schema);
  • a column name cannot be a property name, and no --property or attribute gives it another name. Examples: first name (not a property name) and container (a property of Phalcon\Mvc\Model). The error gives the --property to use (see Names);
  • two columns give the same property name (with camelCase, first_name and firstName): the error tells you to give one of them another name with --property;
  • the base is not valid PHP, or Crest cannot use a RelationAlias or a PropertyName attribute in it (see Relations and Names);
  • the models key of crest.php is not correct, or --property names a column that the table does not have (see Names);
  • a published stub has no {{ columnMap }} or {{ property }}, and the base needs a columnMap() (see Names), or the published model-base has no {{ schema }}, and models.schema has a value (see The Schema);
  • models.getSet is true, and a getter or a setter is a method of Phalcon\Mvc\Model, two properties give one method name, or a published stub has no {{ visibility }} or {{ methods }} (see Getters and Setters);
  • --module names a module that does not exist (see Generating Modules).

What a Module Changes

registerServices() of Module.php changes two services that the providers of the project set:
